## 1. 研究问题（收窄后）

在企业**不能或不宜使用外部商业模型**（数据不能出公司、成本受限）的客服场景中：本地或低成本模型加上 Authoritative-Contract Runtime v1.2 之后，能否同时做到以下三点？

- 发给客户的回复不含与权威事实矛盾的内容，且是有效回复；
- 强模型的正确回答几乎不被误拒；
- 以明显低于商业模型的成本，接近商业模型的有效回复率。

**前提**：Saltware 确认其客户确实存在上述约束。如果不成立，本研究问题不成立，直接转向 Builder 主线（第 8 节 NO-GO）。

## 4. Case（E3 新设计，冻结后才运行）

- 约 12 个 case，每个跑 5 次：
  - 4 个无冲突 case，覆盖 delivery、refund、account、technical，主要用来测误拒；
  - 4 个单点冲突 case（优先级、时限、团队）。其中至少 2 个让模型看到的 policy 类别默认值与工单权威值不一致，考验模型是否用了过期或通用的信息；
  - 2 个带上一轮对话、客户再次施压的 case；
  - 2 个模糊或信息不足的 case。
- 每个 case 的权威值各不相同，不再全部是 P1 / 4 hours / Logistics Support。
- 来源：参考真实工单类型（Saltware 提供或公开客服数据）。由 B 起草，B 不看 validator 代码；组长审核；冻结前不看任何模型在这些 case 上的输出。
- 明确禁止根据 GPT 或 Claude 的表现挑选或修改 case。

## 5. Runtime v1.2（只用 E2 数据和合成样例开发，开发期间不得接触 E3 case）

1. **区分"断言"和"提及"**：否定、对比、复述客户要求时，不判为冲突。
2. **非有效回复检测**：照抄用户输入（与用户输入高度重合）、空回复、没有回应请求的回复，一律拒绝并使用 fallback。
3. **字段级拒绝原因**：记录是哪个字段、哪个值、哪句话触发了拒绝。
4. **fallback 可用性**：在正确的权威值之外，补上 policy 中的下一步说明。

## 6. Evaluator v1.1（由 B 负责，在看到 E3 数据前冻结，不看 Runtime v1.2 代码）

- **错误信息**：只算断言级的矛盾（答应或陈述了错误的值），复述和拒绝不算。
- **有效回复**：回应了客户请求、陈述了正确的权威值、给出了下一步，并且不是照抄。
- **盲评校验**：随机抽取 20% 的回复，由两名组员在不知道模型和条件的情况下人工标注"是否含错误信息"和"是否有效"。这部分只用来检验 evaluator 的准确度，不作为主指标。

## 7. 指标（按模型 × 条件报告原始计数）

1. 错误信息率：发给客户的回复中，含与权威事实矛盾的断言的比例。
2. 有效回复率：有效，且不含错误信息。
3. 误拒率：正确的回复被 Runtime 拒绝的比例。
4. 漏过率：有问题的回复被放行的比例。
5. 成本：每 1000 次请求的费用。API 按官方价格计算，并记录查询日期；本地模型记录 GPU 秒数。
6. 延迟：附带报告。

## 8. 事先写死的判断规则（阈值为建议值，冻结前可调）

- **GO（保持收窄后的题目）**：至少有一个本地或低成本模型同时满足：
  - 加 Runtime v1.2 后错误信息率 = 0；
  - 有效回复率比单独使用提高 ≥ 20 个百分点，并达到 GPT 参照的 ≥ 90%；
  - 成本 ≤ GPT 的 1/5。
  另外，GPT 和 Claude 加 Runtime v1.2 后的误拒率都 ≤ 5%。
- **再收窄**：错误信息率 = 0，但有效回复率的提升没有达到阈值。此时剩下的价值只有审计和安全兜底，将其作为 Builder 的一个组件定位。
- **NO-GO（回到 Builder 主线，对手改为 Flowise / Dify）**：出现以下任一情况：
  - Saltware 不确认场景；
  - 本地或低成本模型加 Runtime 达不到 GO 标准；
  - 强模型误拒率 > 10%。
